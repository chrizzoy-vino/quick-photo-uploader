# `:latest` container tag means the latest release, not the latest main commit

Until now, `cd.yml` pushed `:latest` to GHCR on every push to `main`, and no version tags existed at all — `package.json` sat at `0.1.0` with nothing ever cut as an actual release. Now that the repo is going public and `docker-compose.example.yml` tells operators to pull `:latest` for their deployment, that meaning becomes a problem: `:latest` would silently track work-in-progress `main` commits rather than anything intentionally released, which is not what a stranger pulling the image would expect. We decided to split the tag semantics: a push to `main` now produces only `:edge` and `:sha-<hash>` (a snapshot for testing upcoming changes, e.g. on the maintainer's own homelab, before cutting a release); `:latest` is only set when a `vX.Y.Z` git tag is pushed, alongside the versioned `vX.Y.Z`/`X.Y` tags and an auto-generated GitHub Release (`softprops/action-gh-release` with `generate_release_notes: true`, no hand-maintained `CHANGELOG.md`). Releases are cut manually via `npm version patch|minor|major`, which bumps `package.json` and creates the matching tag in one step, so the two can't drift apart. Considered and rejected: keeping `:latest` tied to `main` and telling operators to pin a version tag instead — rejected because it makes the common case (pull `:latest`, get something stable) the wrong default for a public-facing image. Also considered: dropping the main-push build entirely and only building on release tags — rejected because the `:edge` snapshot is still useful for the maintainer to try out unreleased changes without needing to cut a release first.
